# 0002: バッチ処理基盤 要件定義

- ステータス: Approved
- 起票: 2026-11-23 / 承認: リポジトリオーナー (チャットで「1→2 の順で進めて」)

## 1. 背景・目的
API (同期・短時間) だけでは、大量データの一括処理 (アーカイブ、集計、取り込み) を安全に実行できない。
HTTP のタイムアウト (10 秒) やコネクションプールの制約を受けない、再実行可能なバッチ実行基盤を用意する。

## 2. スコープ
### 対象
- API と domain / repository を共有する独立したバッチ用バイナリ (`batch`)
- ジョブの実行履歴・進捗・チェックポイントの永続化と、途中からの再開
- 同一ジョブの多重起動防止
- サンプルジョブ 2 本
  - `seed`: 大量テストデータの一括投入 (性能試験用)
  - `archive-completed`: 一定期間経過した完了済み Todo をアーカイブテーブルへ移動
- 大量データ (100 万行) での性能計測
### 対象外
- ジョブキュー (SQS / Redis 等) による非同期ジョブ: 将来拡張
- スケジューラ本体: 実行環境 (k8s CronJob / ECS Scheduled Task) に委ねる。設定例のみ提供

## 3. ユーザーストーリー
- 運用者として、DB を止めずに古いデータを安全に退避したい。
- 開発者として、新しいバッチ処理を、チャンク分割・再試行・再開の仕組みを書き直さずに追加したい。

## 4. 機能要件 / 受入条件
| ID | 受入条件 | 優先度 |
|---|---|---|
| AC-1 | Given 完了済みかつ `updated_at` が N 日より前の Todo When `archive-completed --older-than-days N` Then それらが `todos_archive` に移り `todos` から消える。条件外の行は残る | Must |
| AC-2 | 移動はチャンク単位のトランザクションで行い、途中で失敗しても「両方にある」「どちらにもない」行が生じない | Must |
| AC-3 | 同じジョブを 2 回実行しても結果が変わらない (冪等) | Must |
| AC-4 | 同名ジョブが実行中のとき、2 つ目の起動は即座に失敗する (多重起動防止) | Must |
| AC-5 | 各実行は `batch_jobs` に状態 (running / succeeded / failed)・処理件数・チェックポイント・エラーを記録する | Must |
| AC-6 | `--resume <run_id>` で失敗した実行をチェックポイントから再開できる | Must |
| AC-7 | `seed --count N` で N 件をバルク INSERT する。1 文のプレースホルダ数が MySQL 上限 (65,535) を超えない | Must |
| AC-8 | デッドロック・ロック待ちタイムアウト・接続断は指数バックオフで再試行し、上限回数を超えたら failed で終了 (非 0 終了コード) | Must |
| AC-9 | `--dry-run` で対象件数のみ表示し、データを変更しない | Should |
| AC-10 | `status` で直近の実行履歴を表示する | Should |

## 5. 非機能要件
| 区分 | 要件 |
|---|---|
| 性能 | 100 万行の seed と、50 万行のアーカイブがローカル環境で数分以内に完了すること (実測値をレポートに記録) |
| 負荷 | チャンクサイズと同時実行数を引数で調整でき、オンライン API の p95 を大きく悪化させない |
| 運用 | 終了コードで成否を判定できる (0 = 成功)。ログは JSON で出力できる |
